# OmniWriter Review

## 一、总评（3-5 句 + 打分）

OmniWriter 是一款完成度相当高的 AI 写作产品，核心链路（素材输入 → 母稿生成 → 多平台适配 → 一键复制/导出）闭环清晰，工程质量扎实——编辑器的去重回调、图片插入的 iOS 兼容、AI 密钥的 SSRF 防护、双语内容的切分与合并都看得出是踩过坑的。Agent + 场景 + 平台的三层抽象合理，编辑准则内化进 prompt 和校验层的思路是 AI native 的。但目前产品在"极简"和"丝滑"上还有明显的设计冗余：首页信息密度偏高、操作入口分散、AI 生成过程的反馈颗粒度过细反而制造了等待焦虑。整体打 **7.5/10**——底子很好，砍掉 30% 的界面元素和决策点会更接近北极星。

## 二、UX 问题清单

- **[高]** 首页三个独立区块（创作输入 / RewriterLauncher / 最近内容）割裂了"开始创作"这一件事
  - 证据：app/page.tsx:42-92
  - 建议：RewriterLauncher 折叠进 QuickComposer 的一个 tab 或下拉选项；"最近内容"收进侧边栏或底部，首页只留输入框 + 示例。用户来这里就是为了"开始写"，不需要三个入口选一个。

- **[高]** 生成过程四步进度条（素材→规则→生成→检查）+ 实时预览片段 + 交叉验证面板，信息过载反而放大了等待焦虑
  - 证据：components/GenerationProgress.tsx:54-118
  - 建议：极简方案只保留"正在生成"状态 + 一个进度条/百分比 + 停止按钮。交叉验证结果移到生成完成后以"已通过 AI 核查"小字呈现，不放在等待过程中增加心理负担。四步进度对用户没有实际操作价值，只是把内部流程外化了。

- **[中]** QuickComposer 底部三个并排下拉（Agent/风格/模板）+ 示例按钮 + 说明文字，决策点太多
  - 证据：components/QuickComposer.tsx:168-288
  - 建议：默认全部"自动"，且不主动展示这三个选择器。需要修改时通过一个"⚙️ 高级选项"折叠面板展开。绝大多数用户第一次使用不会改这些，展示出来只会增加认知负担。

- **[中]** 平台适配页的"预览/编辑"切换是个伪需求——用户要么直接复制，要么想改，改的时候不需要预览模式
  - 证据：components/PlatformTabs.tsx:220-249
  - 建议：直接默认可编辑的富文本/Markdown 视图，"预览"就是最终复制效果的一瞬间预期，不需要单独一个 tab。或者编辑区上方放一行"复制即带格式"的说明即可。

- **[中]** 移动端顶部导航三个 icon（创作/市场/设置）+ 底部平台操作栏 + 平台 tabs，层级过多
  - 证据：components/AppShell.tsx:137-155、components/PlatformTabs.tsx:142-180
  - 建议：移动端把平台 tabs 吸顶、操作按钮吸底已经是两层了，再加顶部导航就是三层。考虑把"设置"收进侧边滑出菜单，顶部只留 logo + 返回。

- **[低]** "打开空白编辑器"按钮和"空白页直接写"的心智重复
  - 证据：app/page.tsx:70-75
  - 建议：删掉这个按钮。QuickComposer 的输入框本身就是"空白开始"的入口，再加一个空白编辑器按钮是冗余的。

- **[低]** 文章删除需要"hover 出现按钮 → 点击 → 再次点击确认"，交互路径隐晦且不一致
  - 证据：components/AppShell.tsx:97-118
  - 建议：用左滑删除（移动端标准模式）或右键菜单替代。当前 hover 才出现的按钮在触屏上完全不可用。

## 三、UI 问题清单

- **[高]** 玻璃拟态（backdrop-blur + 半透明白）+ 渐变 + 阴影 + 圆角三层叠加，视觉上"重"且不够克制
  - 证据：components/QuickComposer.tsx:145-150、components/GenerationProgress.tsx:37-40
  - 建议：北极星是"极简"，应朝"白底 + 细边框 + 极淡分隔"的方向收敛。Notion / Linear 风格的无阴影、低对比才是极简写作工具的视觉语言。当前的 indigo 渐变 + 多层模糊更像营销落地页，不像生产力工具。

- **[中]** 颜色系统不一致：主色有时用 `indigo-600/700`，有时用 `slate-900 to indigo-700` 渐变，按钮有 `bg-ink`、`bg-indigo-600`、`bg-gradient-to-r from-slate-900 to-indigo-700` 三套
  - 证据：components/QuickComposer.tsx:283-286、components/GenerationProgress.tsx:88、components/PlatformTabs.tsx:175
  - 建议：统一主色体系。要么纯 indigo，要么纯深灰。渐变按钮只留一个主 CTA（提交按钮），其他操作全部用实心/描边二态。

- **[中]** 字号层级过细：有 10px、11px、12px、13px、14px、小屏 16px/大屏 18px，辨识度差且维护成本高
  - 证据：全局 text-[10px] / text-[11px] / text-xs / text-sm / text-base 混用
  - 建议：收敛到 3-4 档字号体系（辅助文字 / 正文 / 标题 / 大标题），用字重和颜色区分层级，而不是 1px 级别的字号差异。

- **[低]** "AI STUDIO" 字样放在 logo 旁像山寨标签
  - 证据：components/AppShell.tsx:60
  - 建议：删掉。产品名就是 OmniWriter，不需要副标题级别的营销 tag 放在导航里。

- **[低]** 首页 H1 渐变色（indigo-700 to sky-500）+ 加粗 + 大号字，和写作工具的"克制"调性不符
  - 证据：app/page.tsx:55-57
  - 建议：纯色就好。渐变是内容产品的审美，不是工具产品的。

## 四、AI 问题清单

- **[高]** 流式生成体验断档：`onText` 回调拿到了实时文本，但只在 GenerationProgress 里显示 3 行预览片段，没有实时写入编辑器
  - 证据：src/lib/ai.ts:118、components/GenerationProgress.tsx:107-110
  - 建议：真正的 AI native 体验是"边生成边可读"——流式直接写入编辑器（可置灰/半透明标记"生成中"），用户可以边看边思考下一步修改，而不是盯着进度条等。当前"完成后一次性写入"的体验和异步调用没区别。

- **[高]** 交叉验证（verdict）的 prompt 和实现逻辑在代码中未见，只有 UI 展示位
  - 证据：components/GenerationProgress.tsx:113-132 有 verdict 渲染，src/lib/ai.ts 中无对应调用
  - 建议：如果还没实现，先不要做 UI 占位。AI 产品最忌讳"承诺了做不到"。要么落地（用第二个模型/调用做事实核查），要么先拿掉，避免用户预期错位。

- **[中]** 系统提示词过长且杂糅：编辑准则 + 风格指南 + Agent 指令 + 平台规则全部堆在 system prompt 里，token 浪费且可能互相稀释
  - 证据：src/lib/ai.ts:110-128 MASTER_SYSTEM 拼接了 EDITORIAL_RULES + STYLE_GUIDE，再加上 Agent directive
  - 建议：按"生成阶段"拆分提示词：生成大纲用一个轻量 prompt，生成正文用带格式约束的 prompt，润色去 AI 味用专门的 refine 步骤。比一次大而全的调用质量更高、也更可控。

- **[中]** 平台适配的重试逻辑（`createDraft` 最多 3 次 + 双语补试 1 次）是"地毯式重试"，没有针对性修复
  - 证据：src/lib/ai.ts:255-272
  - 建议：重试应该带上具体的失败原因（比如"上一版缺少 English Version，请在第 3 段后插入"），而不是重新生成一遍碰运气。当前 retry 只是把同一个 prompt 再发一次，成功率提升有限。

- **[中]** "去 AI 味"是编辑准则的第 3 条，但 prompt 层面的执行依赖模型自觉，没有结构化约束
  - 证据：src/lib/editorial.ts:9
  - 建议：在 refineMaster 之后加一道"AI 味检测 + 自动改写"的后处理：检测"第一/第二/第三"、"值得注意的是"、"这意味着"等高频 AI 套话，自动替换或重组。只靠 prompt 里说一句"去掉 AI 味"是不够的。

- **[低]** 示例文案只有 3 条且偏中文高级用户，新用户不知道"该怎么说"
  - 证据：components/QuickComposer.tsx:25
  - 建议：加更多场景化的短示例（5-8 条），覆盖"粘贴一个链接"、"只写个标题"、"贴一段笔记"等真实输入形态，降低用户心理门槛。

## 五、设计与思路反馈

**产品定位清晰，但抽象层级偏多。** Agent → 场景 → 平台 → 风格 → 模板，五层抽象每一层都有道理，但叠加在一起用户要理解的概念太多了。一个新用户打开首页，需要理解"Agent 是什么"、"场景和 Agent 什么关系"、"风格和模板的区别"，认知负荷不轻。建议：对外只暴露"素材 + 目标平台"两个输入，Agent 和风格全部交给 AI 推断——你已经有 `inferAgentId` 和 `inferPlatformsFromInstruction` 了，为什么还要把选择器摆出来？

**信息架构是"编辑器中心化"的，但首页体验更像"功能导航页"。** OmniWriter 的核心动作应该是"写"——用户打开 App 直接面对一个空白输入框（像 Notion 的空白页、像 iMessage 的聊天框），而不是面对三个区块、六个按钮、一堆说明文字。当前首页的信息架构更像 landing page，不像生产力工具的工作台。

**AI native 程度：偏"AI 辅助写作工具"，还没到"AI 原生写作"。** 区别在哪里？辅助工具是"人写为主，AI 帮改"，AI native 是"AI 出初稿，人做判断和取舍"。OmniWriter 的架构明显是后者——母稿由 AI 生成、平台由 AI 适配、人在最后编辑和复制。但界面语言还是传统编辑器的范式（工具栏、格式按钮、分栏布局），没有体现出"AI 是主要生产者，人是编辑/审核者"的角色反转。

**数据存在本地是对的，但也限制了产品天花板。** localStorage 存储、纯前端架构，部署成本为零、隐私友好——这是优点。但"全平台发布"如果永远停留在"复制粘贴"阶段，价值会打折扣。真正的 AI native 发布应该是一键发布到各平台（通过 API 或自动化），而不是"生成好文案你自己去贴"。当然这涉及平台开放度和账号安全问题，是后话。

## 六、极简+丝滑+AI native 改造方向（只改 3 件）

**1. 首页只剩一个输入框，其他全部折叠或移除。**
删掉 RewriterLauncher 区块、删掉"最近内容"区块（放侧边栏）、删掉 Agent/风格/模板三个下拉（收进一个"高级选项"折叠）、删掉示例按钮下方的两行说明文字。首页就是：一句话标题 + 一个大输入框 + 一个提交按钮 + 三四个示例 chip。像 Claude 的聊天界面、像 ChatGPT 的新对话——用户不需要选择，只需要"说出来"。

**2. 流式生成直接写入编辑器，边生成边读边改。**
把 GenerationProgress 从一个独立面板变成编辑器顶部的一条细状态条（"正在生成 · 312 字"），正文实时流式写入，已生成部分立刻可选、可复制、可发起修改指令。等待时间从"盯着进度条发呆"变成"读一半已经开始想下一步"——这是丝滑的核心，也是 AI native 和传统工具的本质区别。

**3. 砍掉"预览/编辑"二分和所有非必要的格式工具栏，统一成"所见即所得的可编辑稿"。**
平台适配页去掉预览/编辑切换 tab，直接显示最终排版效果的可编辑区域（像 Notion 那样——你看到的就是成品，同时你随时能改）。编辑器工具栏只保留 2-3 个最常用操作，其他全部通过 Markdown 快捷键或 AI 指令完成。目标是：用户打开任何一篇稿子，看到的就是"可以直接复制发布"的状态，而不是"需要切换到预览模式才知道长什么样"。

## 勘误（主控 DSH 修正）

1. **"交叉验证未实现"不成立**：`src/lib/cross-validate.ts`（178 行）已完整实现交叉验证——主模型质检 + 服务端兜底 + codex/claude CLI 降级链路，verdict 从 `/api/generate/stream` 返回。Review 只拿到了 11 个文件没包含它。**改造时应保留该能力，只调整其呈现位置（等待面板 → 完成后摘要）。**
2. **"重试没带失败原因"不成立**：`adaptPlatform` 的 `createDraft(true)` 已追加 `retryRule`（明确告知"上次缺少 English Version，需压缩并补全"），是针对性重试而非地毯式重试。
3. 流式写入编辑器涉及 SSE 管道（`/api/generate/stream` → `generation-events.ts` → article 页面），改动面大，本轮先做**低风险版**：预览片段扩大为可读的实时流面板，保留"完成后一次写入"的落盘语义（防数据丢失），把"边写边编辑"列为二期。
