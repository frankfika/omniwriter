## 0. 裁决结果

**四个待裁决问题的决定：**

1. **WP-A page.tsx 串行：同意**——WP-B 先合（verdict 全权改造 66-69 / 378 / 450 / 690-692 / 标题行润色按钮）；WP-A 后合（onGenerate 函数体 + 1152-1170 布局）；冲突只在 onGenerate 开头的 verdict 那几行，以 B 版本为准
2. **润色：从生成管线拿掉，改成标题行按钮**——直接调 `runRefine(POLISH_INSTRUCTION, 'chief-editor', '润色')`，复用二期 `runRefine` 与 `/api/refine` 管线，零新管线；归 WP-B
3. **流式写入：声明式写法，不加命令式 streamWrite API**——Editor 新增 `streaming?: boolean` prop；服务端每 100ms 节流发 `text: snapshot.slice(lastSentChars)`，客户端无节流；Editor 内部 `setEditable(!streaming)` + `setContent(html, !streaming)`（流式不发 update / 不写 store）；自动滚底仍跟现有 prevHtmlRef 模式；done 时用 `key` 重挂 Editor 一次解决撤销栈残留
4. **备份版本：保持 BACKUP_VERSION=1**——parseBackup 严格相等校验；字段是可选本来就向后兼容，无需 bump

**Claude 现场发现的 5 个关键盲点（必须按方案修复）：**

1. **delta 只发 preview（1500 字尾部）**——前端拼不出全文 → 必须改 SSE 协议：delta 发增量 `text` + `reset` 信号防兜底重试重复
2. **`isArticle` 不校验额外字段是隐患**——verdict.issues 不是数组时 page.tsx:948 `.map` 白屏 → parseBackup 必须清洗 verdict（形状不对删字段不拒备份）
3. **Editor setContent(html, true) 触发 onUpdate → 落 store**——流式期间每拍覆盖 article.content → done 时 `setContent(html, true)` + 用 `key` 重挂；流式期间必须 `setContent(html, false)`（不触发 update）
4. **AgentCompose:211 / BriefPanel:178 是死分支**——page.tsx:1159 只在 `!generating` 时渲染 briefPanel，进度条永远不可见 → 删掉
5. **润色放在生成管线是死代码 / 与 WP-A 冲突**——用户看流式正文写完后再被整篇替换，体验崩坏 → 改标题行按钮

**其他调整：**
- **不加 `store.setVerdict`**——直接用 `update(id, { verdict })`，再包一层是多余的
- **WP-B 不需要切文章回放 verdict 的 useEffect**——直接写成 `const verdict = article?.verdict ?? null` 派生，同步问题自然消解
- **停止生成语义统一**——生成前原稿为空就保留已写入部分落 store；原稿不为空就恢复原稿并提示「已停止，原稿没有被覆盖」
- **大纲阶段只在 `length !== 'short'` 启用**——max_tokens 600，超时 20 秒，失败静默降级；不引入「丝滑倒退」问题
